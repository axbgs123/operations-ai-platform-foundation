# TikHub 公开作品数据采集

## 用途

TikHub 在本项目中只承担“公开数据采集层”：运营人员发布内容后，将抖音或小红书公开作品链接绑定到平台内容，系统按发布后 1 小时、24 小时、3 天和 7 天采集公开互动数据，并写入原有数据快照与分析流程。

本功能不会自动发布内容，不需要平台 Cookie，也不读取创作者后台的非公开指标。

## 当前流程

1. 管理员在“工作区设置 → 公开数据采集”中保存 TikHub API Key、接口区域和每日调用上限。
2. 点击“测试连接”，通过后进入一条内容的“数据快照”标签。
3. 粘贴公开作品链接并填写发布时间；无法自动解析时可补充平台作品 ID。
4. 系统建立 1h、24h、72h、7d 四个采集任务。错过早期节点的旧作品只立即补采一次，不伪造历史时点数据。
5. 每次采集同时保存供应商原始响应、接收时间、供应商接口合同和标准化指标，再创建已确认的数据快照。
6. 自动分析已开启时，新快照会沿用现有分析流程；采集失败最多重试三次，也可以由运营人员手动点击“立即采集一次”。

## 架构边界

- 业务层依赖 `PublicDataProvider` 合同，TikHub 是第一个实现；后续可增加其他供应商而不改内容和快照模型。
- API Key 只在 FastAPI 后端加密保存，Web 页面只能看到“已配置”状态。
- 抖音与小红书使用独立解析与指标映射，不跨平台混算。
- 每个工作区单独计算每日调用次数，包括连接测试、作品解析和指标采集。
- 当前自动调度器运行在 API 进程内，适合本项目的单实例轻量部署。未来扩展为多 API 实例时，应迁移到独立调度 Worker。

## 数据表

| 表 | 作用 |
| --- | --- |
| `public_data_provider_configs` | 工作区 TikHub 配置、连接状态、每日额度和当日用量 |
| `published_content_bindings` | 平台内容与公开作品 URL/ID 的绑定 |
| `public_collection_jobs` | 1h、24h、72h、7d 和人工补采任务 |
| `public_collection_attempts` | 每次采集尝试、错误码和供应商请求 ID |
| `public_observations` | 原始响应、采集时间、响应哈希和标准化指标 |
| `data_snapshots` / `snapshot_metric_values` | 进入既有运营分析的数据快照与指标值 |

## 当前不包含

- 自动发布、平台账号密码或 Cookie 托管。
- 创作者后台私有指标回收。
- 对标账号、评论需求分析、运营日报和爆款预警。这些能力在作品数据链路稳定后分阶段接入，同样复用供应商适配器与快照数据。
- TikHub 之外供应商的具体 Adapter。

TikHub 是第三方非官方数据服务。使用者需要自行申请密钥、承担调用费用，并确认自己的使用场景符合平台规则和当地法律。
