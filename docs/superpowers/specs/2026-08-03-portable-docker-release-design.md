# 运营工具跨平台便携包设计

**日期：** 2026-08-03  
**状态：** 待用户书面复核  
**目标：** 为 Windows 和 macOS 提供同一套可搬家安装包，并为后续 GitHub 开源发布建立可重复、无敏感数据的打包流程。

## 1. 用户目标

用户需要把完整运营工具搬到另一台 Windows 或 macOS 电脑。新电脑安装 Docker Desktop 后，应能通过解压和双击脚本完成首次启动，不需要分别安装 Python、Node.js、PostgreSQL、Redis 或 MinIO。

便携包必须提供可写的真实本地工作区，不能只打开只读 Demo。首次启动生成的管理员邀请码只保存在用户电脑，不进入源码、Git 历史、公开 Release 或日志。

## 2. 选择的方案

采用单一 Docker Compose 便携包，不分别维护 Windows 和 macOS 原生应用。

原因：

- 现有项目已经具备经过验证的 Docker Compose、迁移、健康检查、Demo 种子和持久化卷。
- Windows、Intel Mac 和 Apple 芯片 Mac 可以复用相同源码和业务容器。
- 数据库、队列、对象存储、API、Worker 和 Web 的版本可以统一冻结。
- 后续开源时，源码仓库和 GitHub Release 可以由同一构建流程生成。

不选择原生安装器，因为它需要分别封装后台服务、数据库和系统权限，维护和验收成本显著更高。不选择虚拟机镜像，因为体积大、性能差且不适合 GitHub Release。

## 3. 交付物

每个版本生成一个 ZIP：

```text
operations-ai-portable-<version>/
├── 启动运营工具-Windows.bat
├── 停止运营工具-Windows.bat
├── 启动运营工具-macOS.command
├── 停止运营工具-macOS.command
├── 使用说明.txt
├── checksums.txt
├── release-manifest.json
├── apps/
├── infra/
├── packages/
├── scripts/
├── docs/
├── tests/
├── .env.example
├── package.json
├── pnpm-lock.yaml
└── 其余运行所需的受控源码文件
```

ZIP 不包含 `.git`、`.env`、本地工作区状态、真实数据库、Docker 卷、备份、日志、API Key、邀请码、Cookie、令牌、`node_modules`、Python `.venv`、构建缓存或 `.superpowers/brainstorm`。

## 4. 启动流程

Windows 和 macOS 启动脚本执行相同状态机：

1. 定位脚本所在目录，避免用户从其他目录双击时找不到文件。
2. 检查 Docker Desktop 和 Docker Compose v2；缺失时显示中文安装提示并安全退出。
3. 首次运行时从 `.env.example` 创建本地 `.env`，但不覆盖用户已有配置。
4. 使用固定本地 Compose 项目名启动 PostgreSQL、Redis、MinIO、迁移、Bucket 初始化、Demo 种子、API、Worker 和 Web。
5. 等待 `/health/ready` 和 Web 首页可访问；超时后显示安全诊断命令，不伪装成功。
6. 如果本地尚无初始化记录，调用正式工作区创建 API 创建一个可写工作区。
7. 把工作区地址和一次性管理员邀请码写入本机 `首次登录信息.txt`；Windows 同时复制到剪贴板，macOS 在 `pbcopy` 可用时复制。
8. 打开 `http://127.0.0.1:3000/enter`。若浏览器打开失败，仍打印可手动访问的地址。

重复启动必须幂等：不得重复覆盖 `.env`、重复创建工作区或删除既有 Docker 卷。

停止脚本只执行正常 `docker compose down`，保留数据库、Redis 和对象存储卷。便携包不提供双击“删除全部数据”入口，避免误删；彻底清理只能按文档手动执行。

## 5. 工作区初始化与数据边界

首次工作区初始化使用现有正式 `POST /v1/workspaces` 合同，不新增隐藏注册方式，也不绕过权限。

本地状态目录仅保存：

- 已初始化标记；
- 工作区 ID；
- 本机入口地址；
- 首次管理员邀请码文件。

邀请码属于敏感信息：

- 文件只在本机运行时生成；
- 目录加入 `.gitignore`、源码发布拒绝清单和密钥扫描；
- 不写入 Docker 镜像、打包产物、测试快照或普通日志；
- 使用说明提醒用户首次登录后妥善保管，并通过后台签发独立成员邀请码。

运营数据继续保存在 Docker 持久化卷。跨电脑迁移真实数据应使用产品内的 ZIP 完整备份与恢复功能，不把运行卷或数据库 dump 混入便携安装包。

## 6. 配置与资源要求

默认使用 Mock 模型，不需要千问 API Key，也不会产生模型费用。用户后续可以在工作区设置中自行配置千问 Key 和预算。

最低建议：

- Docker Desktop 与 Docker Compose v2；
- 8 GB 物理内存，运行时通常约占 1.5–3 GB，首次构建峰值可能达到 4–6 GB；
- 10 GB 可用磁盘，用于基础镜像、构建缓存和持久化数据；
- 首次启动可访问容器镜像和依赖源；
- 默认端口 3000、8000、55432、9000、9001 可用。

端口冲突、Docker 未启动、磁盘不足、迁移失败或服务未就绪必须给出中文提示和诊断命令。

## 7. GitHub 发布策略

仓库当前保持私有，完成人工验收和发布阻断项后再切换为公开。

公开时同时提供：

1. 完整源码和 Git 历史；
2. Apache-2.0 许可证和第三方依赖边界；
3. GitHub Release 中的跨平台 ZIP、SHA-256 和 manifest；
4. Docker 快速开始与常见故障说明；
5. 明确声明真实千问、真实平台页面、Windows/Edge 和独立非开发者验收的实际状态。

GitHub Actions 仅在版本标签触发便携包构建。工作流使用最小只读源码权限和 Release 写权限，不接受未受控外部脚本，不上传环境变量、测试数据库或用户数据。

## 8. 构建边界

新增确定性便携包构建器：

- 输入必须是已提交的 Git 树；
- 文件来源使用递归 allowlist；
- 拒绝符号链接、超限文件、密钥特征、私有资料和未登记二进制；
- 生成稳定排序的 `release-manifest.json`；
- 为全部文件生成 SHA-256；
- 固定 ZIP 内路径和时间戳，减少无意义哈希漂移；
- 同一提交重复构建应得到相同内容哈希。

本地未提交文件默认拒绝进入正式 Release。现有受保护的 `.superpowers/brainstorm` 永远不进入安装包或提交。

## 9. 验证

### 自动化测试

- 构建器先通过失败测试证明会拒绝密钥、`.env`、数据库、符号链接、未登记文件和路径穿越。
- 验证 Windows/macOS 启动脚本均存在，macOS 脚本保留可执行权限，Windows 脚本使用兼容换行。
- 解压后执行现有 Compose 配置、迁移、Schema consistency、密钥扫描和发布 allowlist 检查。
- 从随机临时目录解压包，在随机 Compose 项目和端口中完成 fresh install。
- 验证首次创建工作区、重复启动不重复创建、停止后数据保留、重启后仍可进入。
- 验证停止脚本不删除卷，打包产物不包含本地状态或首次登录信息。
- 验证 API、Web 和扩展现有回归不受影响。

### 平台验收

- macOS：在当前 Mac 上实际解压、启动、登录、停止和重启。
- Windows：先完成静态脚本和容器合同验证，再在真实 Windows + Docker Desktop 环境执行人工验收；未完成前文档标记为 `not_run`，不得宣称已验证。
- Intel Mac：依赖镜像支持情况按实际结果记录；未实测时不作保证。

所有测试环境使用随机、可识别的临时资源，完成后只清理本任务创建的容器、网络、卷和临时目录。

## 10. 错误处理

- Docker 缺失：提示官方下载入口和安装后重新运行。
- 端口占用：列出冲突端口，不自动终止其他程序。
- 构建或镜像下载失败：保留现有卷，显示重试命令。
- 迁移失败：API/Web 不启动，防止旧结构运行。
- 工作区初始化失败：平台仍可打开 Demo，但不得伪造真实工作区成功；保留可重试初始化入口。
- 浏览器无法自动打开：显示手动地址，不视为服务失败。

## 11. 非目标

本任务不制作免 Docker 的 Windows EXE、macOS DMG、桌面客户端或虚拟机镜像；不携带真实运营数据；不调用真实千问；不完成真实抖音/小红书自动化；不把尚未完成的 Task 9B 宣称为通过。

## 12. 验收标准

- 一个 ZIP 同时包含 Windows 和 macOS 启停入口。
- 新电脑安装 Docker 后可以解压并启动完整服务。
- 首次运行能够创建可写工作区并提供本机管理员邀请码。
- 重复启动、停止和重启不会丢失数据或重复初始化。
- 包内不存在密钥、真实数据、本地缓存和开发环境目录。
- macOS 实际 fresh-install 通过；Windows 状态按真实验收诚实记录。
- 产物附带 SHA-256、manifest 和中文说明。
- GitHub 私有阶段可保存产物；公开阶段可以由标签确定性生成 Release。
