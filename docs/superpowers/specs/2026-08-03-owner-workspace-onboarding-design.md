# 团队管理者免邀请码入驻设计

## 1. 目标

把真实工作区入口拆成两条清晰路径：

1. 团队管理者创建新团队时，填写团队名称和自己的显示名称，不需要邀请码；创建成功后立即成为该团队的首位管理员并进入工作区。
2. 其他成员加入已有团队时，填写自己的显示名称和管理员单独签发的邀请码；角色由邀请码决定。

“免邀请码”只适用于创建新团队的首位管理员，不允许任何人仅凭名称进入已经存在的团队。

## 2. 已确认的产品规则

- 每个团队对应一个独立 Workspace。
- 创建团队需要 `workspace_name` 和 `display_name`。
- 创建成功时必须在同一数据库事务中创建 Workspace、首位 Admin Member 和 Workspace Session。
- 服务端设置安全会话 Cookie，并只向前端返回 `workspace_id`、`member_id` 和 CSRF Token。
- 创建流程不签发、返回、记录或展示“初始管理员邀请码”。
- 管理员进入工作区后，可以按现有规则分别生成 Admin、Editor 或 Viewer 邀请码。
- 邀请码继续保持一人一码、角色固定、仅显示一次、可单独撤销，不能成为一个长期复用的“团队通用密码”。
- 被邀请成员自行填写显示名称；邀请码不携带显示名称。
- 不同团队的成员、会话、邀请码和数据继续严格隔离。
- Demo 入口和私有团队入口继续隔离。

## 3. 入口体验

`/enter` 使用明亮工作台视觉，提供两个持续可见的入口，不采用只在首次出现的引导：

### 创建团队

- 字段：团队名称、我的名称。
- 主按钮：`创建团队并进入`。
- 辅助说明：`你会成为这个团队的管理员，创建团队不需要邀请码。`
- 成功后保存 CSRF Token 到现有 sessionStorage 边界，并跳转到工作台总览。

### 加入团队

- 字段：邀请码、我的名称。
- 主按钮：`加入团队`。
- 辅助说明：`向团队管理员获取属于你的独立邀请码。`
- 继续调用现有邀请登录接口，成功后进入工作台总览。

两个表单分别维护 loading、错误和禁用状态；一个请求进行中时不得重复提交。错误文案只说明稳定原因，不暴露邀请码、会话 Token、数据库信息或内部异常。

## 4. 服务端设计

新增专用合同：

```http
POST /v1/workspaces/onboard
Content-Type: application/json

{
  "workspace_name": "C哥内容团队",
  "display_name": "小白"
}
```

成功响应沿用 `SessionCreated`：

```json
{
  "workspace_id": "uuid",
  "member_id": "uuid",
  "csrf_token": "opaque"
}
```

同时设置现有 `session` HttpOnly Cookie。核心服务新增一个原子方法，顺序为：

1. 校验两个名称的长度和空白归一化结果。
2. 创建 Workspace。
3. 直接创建角色为 `admin` 的 WorkspaceMember。
4. 创建 WorkspaceSession。
5. 写入 `workspace.created`、`member.owner_created` 和 `session.created` 的安全审计事件。
6. 提交后才返回成功。

任何一步失败都整体回滚，不允许留下无管理员 Workspace、无会话管理员或孤立会话。

现有 `POST /v1/workspaces` 暂时保留兼容已有内部测试和工具，但新版 `/enter` 与便携启动器不得再使用它生成初始管理员邀请码。后续公开 API 收敛可另立迁移任务，不在本次便携发布收尾中扩大范围。

## 5. 滥用与安全边界

- 新建团队接口归入现有 AUTH 限流类别。
- 仅允许同源浏览器请求；沿用现有生产环境 Cookie 安全配置。
- 名称只作为显示数据，不作为身份凭证。
- 创建者的身份凭证是服务端签发的随机会话 Token，而不是名称。
- 清除浏览器数据、会话过期或换电脑后，管理者不能只凭名称重新进入已有团队；必须使用另一个管理员签发的独立 Admin 邀请码。产品文案需明确这一恢复边界。
- 新建团队不影响、枚举或搜索任何已有团队。
- 响应、日志、URL、备份和产品事件不得包含 Session Token、邀请码或 Cookie。

## 6. 便携启动器调整

Task 1 的启动器不再代替用户创建“本地运营工作区”，也不再生成：

- `.local-state/bootstrap.json`
- `.local-state/首次登录信息.txt`
- 初始管理员邀请码或剪贴板内容

启动器只负责：

1. 检查 Docker 与 Compose。
2. 创建但不覆盖 `.env`。
3. 启动服务并等待 API、Web 就绪。
4. 打开 `/enter`。
5. 正常停止时保留数据卷。

`.local-state/` 继续作为发布包未来本机状态的禁止提交边界，但本次入口不依赖其中的敏感凭据。

确定性 ZIP 构建器继续保持 Task 2 的 tracked-only、禁止路径、换行、权限、manifest 和 checksum 约束；修改启动器后必须重新构建并产生新的确定性哈希。

## 7. 测试与验收

### API

- 创建团队无需邀请码即可返回 Admin Session。
- Workspace、Admin Member、Session 和审计事件在一个事务内创建。
- 失败注入后四类记录均不残留。
- 首位成员角色固定为 Admin。
- 新建团队接口受 AUTH 限流。
- 响应不包含管理员邀请码、Session Token 或 Cookie 明文。
- 创建两个团队后，双方会话不能跨工作区读取。
- 现有成员邀请码登录、角色和撤销回归保持通过。

### Web

- `/enter` 同时提供“创建团队”和“加入团队”。
- 两条路径的名称均由使用者填写。
- 创建成功后保存 CSRF Token 并进入对应工作区总览。
- 加入成功后保持现有邀请语义。
- 请求中禁用重复提交；失败后可安全重试。
- 页面明确说明：免邀请码仅用于创建团队；以后换设备需管理员邀请码。
- 390px 宽度下两条入口和错误信息可完整操作。

### Portable

- macOS 和 Windows 启动器不再调用 `POST /v1/workspaces`。
- 启动器、普通日志、剪贴板和本机文件均不产生初始邀请码。
- Task 1 启动合同、Task 2 构建器、安全扫描和确定性构建全部重新通过。
- Task 3 使用解压后的 macOS 包，从 `/enter` 创建团队并验证 Admin 权限、重启持久化和成员邀请码加入。
- Windows 仍保持 `not_run`，直到真实 Windows + Docker Desktop 人工验收。

## 8. 非目标

- 不增加账号密码、手机号、邮箱或第三方登录。
- 不允许通过团队名称查找或加入团队。
- 不创建可长期共享的团队通用邀请码。
- 不实现管理员找回、跨设备无凭证登录或云端账号体系。
- 不改变 Demo、真实千问、真实平台页面或 Windows 实机验收状态。
