## 1. 背景

当前产品已经具备账号与栏目管理、数据导入、内容分析、爆款素材、账号风格、事实资料、标题文案与封面生成、发布前风控、任务运维、导出和备份等能力，但运营人员仍需要自己判断：

1. 今天最值得先处理哪个账号和哪条内容。
2. 应该进入哪个模块查看原因。
3. 分析完成后应该继续调用哪些能力。
4. 生成结果是否引用了正确事实、风格和平台规则。
5. 任务失败、外部 API 用量异常或会修改正式数据时应该如何继续。

运营智能体的目标不是增加一个通用聊天框，而是把现有模块组织成一条可解释、可批准、可恢复的运营工作流。第一版以“每日巡检并生成一份优化草稿”为唯一主闭环，不操作抖音或小红书后台，不提供自动发布能力。

## 2. GitHub 开源调研与采用决策

开发前对 GitHub 上的同类产品和智能体基础设施进行了核对。结论是：已有项目分别覆盖社媒生成发布、团队排期、人工审批、小红书数据工具和每日简报，但没有发现一个项目同时覆盖本产品的“双平台历史数据巡检、确定性问题排序、事实与风格约束、RiskRAG、一次计划批准、分级动作确认和不自动发布”闭环。

| --- | --- | --- | --- |
| [LangChain Social Media Agent](https://github.com/langchain-ai/social-media-agent)（MIT） | 人工介入、接受/修改/拒绝、可暂停工作流 | 以 URL 转社媒帖子和排期发布为中心；依赖 LangGraph、LangSmith、Arcade、Firecrawl 等外部服务 | 借鉴批准与中断语义，不复制技术栈，不接发布能力 |

### 2.1 架构结论

1. 不为了“像智能体”而引入 LangGraph 或另一套 Agent OS。现有 FastAPI、Celery、任务租约、fencing、用量治理和审计能力已经覆盖第一版需要的执行基础。
2. 新增“待确认事项”视图，将计划批准、正式数据覆盖和移入回收站分别展示；确认必须绑定运行、步骤和参数指纹。
3. 执行页使用可恢复的步骤时间线，明确展示 `等待执行 / 执行中 / 等待确认 / 已完成 / 失败 / 已跳过`，刷新或重启后从服务端恢复，不能仅依赖聊天消息。
4. 工具目录采用版本化 Adapter 边界。未来若接官方平台 API、MCP 或桌面 Agent，只能新增受控 Adapter，不能让模型获得 Cookie、任意 URL 或电脑控制权。
5. 第一版的每日建议来自本产品数据库中的正式运营证据。外部热点搜索、竞品抓取和自动发布均不进入第一版，也不能影响确定性优先级。
6. 许可证边界：可参考公开产品交互和通用思想；复制 MIT 代码时必须保留许可声明；不复制 AGPL 项目代码；无明确许可证的仓库只用于调研。
7. 开源版本不提供充值、套餐、代付或平台计费。使用者自行配置模型供应商 API Key，并直接承担供应商产生的费用；产品只提供用量限制、调用记录和异常保护。

## 3. 产品定位

运营智能体定位为“运营主管”，同时具备两个入口：

1. 工作台首页的“今日运营建议”：根据团队当前状态主动指出一项最高优先级行动。
2. 独立的“运营智能体”入口：用户可以输入目标，并查看计划、执行进度、确认请求和最终产物。

智能体可以查看整个团队的状态，但执行写操作时必须锁定一个平台账号。抖音和小红书的数据、指标、风格、事实引用和风险资料继续严格隔离。

## 4. 设计目标

1. 用户进入工作台后，可以在十秒内知道今天最值得先处理什么。
2. 用户只需批准一次完整计划，低风险步骤即可连续执行。
3. 覆盖正式数据和移入回收站必须在动作发生前再次确认。
4. 每个结论都能追溯到账号数据、内容、事实、风格、爆款素材或风险证据。
5. 每次执行都固定平台、账号、数据截止时间、规则版本、模型配置和计划版本。
6. 任务失败后从安全检查点恢复，不能重复执行已经成功的外部 API 调用。
7. Viewer、Editor、Admin 看到的计划和操作必须符合真实服务端权限。
8. 用户最终获得可保存或导出的优化草稿，但仍由运营人员手动前往平台发布。

## 5. 非目标

第一版明确不实现：

1. 自动登录或操作抖音、小红书创作者后台。
2. 自动发布、定时发布、评论回复或私信操作。
3. 无需批准的全自动长期运行。
4. 自由访问数据库、对象存储、系统 Shell 或任意 URL。
5. 让模型自行发明工具、接口、权限或账号范围。
6. 跨平台合并播放量、曝光量、点击率等不可比较业务指标。
7. 永久删除工作区、清空回收站或绕过现有保留策略。
8. 用智能体结论替代人工发布判断或平台审核。
9. 第一版后台定时巡检；巡检只在打开工作台或用户手动刷新时按需运行。

## 6. 已批准的核心闭环

第一版只验收以下端到端闭环：

1. 用户打开工作台。
2. 系统按需读取团队状态，生成候选问题并确定一项最高优先级建议。
3. 用户查看建议的原因、数据截止时间、目标账号和完整执行计划。
4. 用户点击“批准计划”。
5. 智能体锁定一个平台账号并执行低风险步骤。
6. 真实模型调用在已批准计划和工作区用量政策范围内直接执行；如需覆盖正式数据或移入回收站，智能体暂停并请求单独确认。
7. 智能体完成分析、生成优化草稿并执行发布前检查。
8. 页面展示结果、引用、风险状态、API 用量记录、失败步骤和下一步人工操作。
9. 用户保存或导出标题、文案、封面建议和分析结论，再手动前往平台发布。

一次巡检只突出一个最高优先级行动。完成、拒绝或暂缓后，系统才展示下一项建议。

## 7. 巡检与优先级

### 7.1 触发方式

第一版不使用定时任务。以下行为触发巡检：

1. 成员当天首次打开工作台。
2. 用户点击“重新巡检”。
3. 上次巡检后出现新的正式快照、分析结果、高风险扫描、失败任务或账号配置版本。

同一工作区、同一数据版本和同一算法版本的结果可以复用，避免重复计算和模型费用。页面必须显示 `数据截止时间`，数据过期或样本不足时直接说明，不能伪装成最新判断。

### 7.2 候选信号

巡检从以下信号生成候选问题：

1. 数据完整度不足或快照成熟度不满足分析条件。
2. 存在尚未分析或分析版本过期的内容。
3. 同账号、同平台、同口径数据出现异常变化。
4. 存在已确认、可复用的爆款结构或风格机会。
5. 存在高风险、OCR 低置信度、无有效证据或待复检内容。
6. 导入、分析、生成、恢复等后台任务失败或等待配置。
7. 账号目标、栏目优先级或临时活动规则要求优先处理。
8. 相同问题近期已经执行、拒绝或暂缓，需要降低重复推荐权重。

### 7.3 排序规则

第一版使用确定性候选生成和排序，不允许大模型直接决定优先级。排序按以下顺序比较：

1. 是否阻断当前运营闭环。
2. 风险严重度和是否需要人工处理。
3. 是否存在足够且新鲜的数据证据。
4. 对账号目标和当前栏目优先级的影响。
5. 是否能通过现有工具形成完整可执行闭环。
6. 最近是否已处理或被用户拒绝。

大模型只负责把已确定的候选、依据和步骤转写为易懂说明，不能增加未进入候选集的结论。专业模式保留候选类型、版本和原始安全状态。

## 8. 计划生成与批准

### 8.1 计划内容

批准前必须展示：

- 本次目标。
- 锁定的平台和账号。
- 数据截止时间和样本范围。
- 为什么优先处理。
- 将调用的工具及执行顺序。
- 哪些步骤会调用使用者自行配置的外部 API，以及预计消耗的用量。
- 哪些步骤可能修改正式数据。
- 预计产物。
- 无法自动完成的人工步骤。

计划是严格结构化数据，不接受模型返回的任意工具名、任意 URL 或自由代码。计划创建后固定 `plan_version`、输入指纹、账号配置版本、模型配置版本、风险规则版本和工具目录版本。

### 8.2 批准行为

用户批准的是一份不可变计划。批准后若平台、账号、关键输入、工具参数、模型配置或规则版本发生变化，原批准自动失效，必须生成新计划并重新批准。

批准权限：

- Viewer：只能查看建议、计划和已完成结果。
- Editor：可以批准读取、分析、生成草稿和发布前检查。
- Admin：除 Editor 能力外，可以管理模型配置与用量上限，并批准正式数据覆盖、关键配置修改和移入回收站。

前端隐藏按钮不能替代服务端鉴权。跨工作区、跨平台或账号不匹配统一按现有安全规则返回 404。

所有等待人工处理的动作进入统一“待确认事项”，每项展示动作名称、目标账号、参数安全摘要、是否调用外部 API、是否修改正式数据、过期时间和允许的响应。第一版固定支持 `批准`、`拒绝`；计划批准前允许返回修改目标，动作执行中的关键参数不得原地编辑，必须拒绝后生成新步骤，避免批准对象与实际执行对象不一致。

## 9. 第一版工具目录

智能体只能调用服务端注册的版本化工具。每个工具必须声明输入 Schema、输出 Schema、所需权限、风险等级、幂等方式、是否调用外部 API 和是否支持安全重试。

### 9.1 自动执行的低风险工具

- 读取工作台、账号仪表盘和账号目标。
- 读取内容详情和正式数据快照。
- 读取分析队列、发布前检查队列和后台任务状态。
- 发起或读取运营分析。
- 检索已确认事实、账号风格和已确认爆款素材。
- 创建或修改智能体本次运行产生的草稿。
- 对草稿执行事实检查和发布前风险检查。
- 保存建议、草稿和执行摘要。
- 生成受控导出结果。

### 9.2 需要动作前确认的工具

- 覆盖已经确认的正式运营数据。
- 修改已确认事实、账号配置、栏目规则或关键模型配置。
- 将内容或素材移入回收站。

确认必须绑定具体运行、步骤、参数摘要、工作区版本、成员和有效期。确认不能复用于其他步骤，也不能授权永久删除工作区。

真实千问文本、视觉、OCR、Embedding 或图片生成能力不作为单独付费商品，也不要求每次额外确认。它们只能使用 Admin 自行配置的 API Key，并受工作区用量政策、每日上限、并发限制和已批准计划约束。超出上限时停止执行，不提供平台充值或绕过限制的入口。

### 9.3 不提供给智能体的能力

- 任意 SQL、Shell、文件系统或网络请求。
- 邀请码、会话、Cookie、API Key 和密钥读取。
- 永久删除、清空回收站和工作区删除。
- 平台登录、发布、评论、私信或其他电脑控制。
- 绕过事实门禁、RiskRAG、用量政策或角色权限。

## 10. 执行状态机

运行状态：

`draft → awaiting_plan_approval → queued → running → awaiting_action_confirmation → running → succeeded`

终止状态：

- `rejected`：用户拒绝计划。
- `cancelled`：在安全检查点取消。
- `failed`：不可恢复错误。
- `configuration_required`：缺少模型配置、用量政策、事实或其他必要配置。
- `compensation_required`：正式写入失败且自动补偿未完成。

每个步骤独立记录：

- 工具和合同版本。
- 输入指纹和安全摘要。
- 状态、开始时间和完成时间。
- 幂等键、attempt 和安全错误码。
- 外部 API 用量 reservation、最终用量或 unknown 状态。
- 产物 ID、证据引用和下一步。

旧 Worker 必须通过现有 claim、lease、heartbeat 和 operation fencing 机制阻止覆盖新状态。供应商已可能计费但结果不确定时进入 `provider_outcome_unknown`，不能自动重试。

Web 端从服务端步骤记录构建时间线，不把聊天记录作为执行真相。页面刷新、浏览器关闭、应用重启或 Worker 接管后，必须恢复相同运行、当前步骤和待确认项。

## 11. 数据与模块边界

### 11.1 新模块

在现有 FastAPI 模块化单体中新增独立 `operations_agent` 模块，负责：

- 巡检候选聚合。
- 确定性优先级排序。
- 结构化计划生成。
- 工具目录和权限校验。
- 运行状态机。
- 确认与审计。
- 产物关联。

该模块调用现有 Workbench、Analysis、Generation、Style/Facts、RiskRAG、Exports、Models 和 Operations 的公开服务接口，不复制这些模块的算法，不跨模块直接拼接私有查询。

### 11.2 建议数据模型

- `agent_briefings`：工作区、日期、输入版本、候选摘要和最高优先级建议。
- `agent_plans`：不可变计划、账号范围、版本、输入指纹和批准状态。
- `agent_runs`：运行状态、当前步骤、创建者和锁定范围。
- `agent_run_steps`：追加式步骤、工具版本、结果和安全错误。
- `agent_confirmations`：一次性动作确认及参数指纹。
- `agent_artifacts`：分析、草稿、风控扫描和导出结果的引用。
- `agent_events`：追加式审计事件和状态变化。

正文、Prompt、图片和模型输出继续保存在对应业务记录或对象存储中。智能体表只保存必要引用和安全摘要，不复制敏感正文。

## 12. 页面与交互

### 12.1 工作台首页

在现有“下一步行动”区域升级为“今日运营建议”，包含：

- 建议标题。
- 目标平台和账号。
- 一句话优先原因。
- 数据截止时间。
- `查看计划` 主按钮。
- `暂缓` 和 `不再推荐此类问题` 次级操作。

没有足够数据时显示明确的准备动作，例如“先导入一次发布后的表现数据”，不能生成虚假建议。

### 12.2 智能体页面

新增正式入口 `/workspaces/{workspace_id}/agent`，页面分为：

1. 目标与范围：用户目标、团队概览和锁定账号。
2. 执行计划：依据、步骤、外部 API 用量说明和风险确认。
3. 任务进度：当前步骤、已完成步骤、等待确认、失败和重试。
4. 最终产物：优化标题、文案、封面建议、风险结果、引用和导出。

对话是输入目标和追问结果的界面，不是无边界聊天。历史消息只围绕具体 briefing、plan 或 run 展示。

### 12.3 待确认事项

智能体页提供独立“待确认事项”区域，并在工作台顶部显示数量。用户不需要从聊天记录中寻找确认请求。已处理、过期和因版本变化失效的请求保留安全审计状态，但不能再次批准。

### 12.4 易懂与专业模式

易懂模式说明“为什么建议先做”“正在做什么”“需要你确认什么”。专业模式补充工具版本、模型、证据、状态码和 API 用量记录，但两种模式的权限、风险和执行结果完全一致。

移动端支持查看建议、批准普通计划、查看进度和结果。复杂封面编辑、模型 API Key 与用量上限、正式数据覆盖和回收站确认继续提示使用电脑端。

## 13. 最终产物

第一版成功运行至少产生：

1. 一份问题诊断和数据依据。
2. 一份经过用户批准的执行计划。
3. 一份优化后的标题和文案草稿。
4. 在问题相关时生成封面建议或受控封面草稿。
5. 一次事实检查和发布前风险检查结果。
6. 一份执行摘要，区分自动完成、人工确认和仍需人工处理的步骤。

产物必须标注平台、账号、内容、事实版本、风格版本、模型模式和数据截止时间。高风险、OCR 失败、证据不足或事实冲突继续 fail-closed，不能显示为“可以发布”。

## 14. 错误处理

1. 数据不足：停止在计划前，给出需要补充的数据和入口。
2. 账号范围变化：使计划批准失效，重新生成计划。
3. 模型未配置或用量上限不足：进入 `configuration_required`，不回退 Mock 冒充真实结果。
4. 外部 API 结果不确定：保留 unknown 用量，不自动重试，避免重复消耗使用者额度。
5. 工具暂时失败：在安全重试上限内重试，超过上限进入失败并给出安全错误码。
6. 风控或事实门禁失败：保留已完成产物，但阻止保存为完成的优化包。
7. 用户取消：只在安全检查点终止；已经成功的正式写入和 API 用量记录不回滚伪装成未发生。
8. 权限被撤销：立即停止后续步骤，旧确认失效。
9. Worker 崩溃：通过租约和 fencing 由新 Worker 接管，不重复发布旧结果。

## 15. 隐私、安全与外部 API 用量

1. 所有查询必须绑定 `WorkspaceContext`、平台和账号。
2. Prompt、标题、文案、图片、OCR 原文、密钥和供应商错误正文不得进入普通日志。
3. 智能体不能读取模型密钥明文；密钥只在现有 Adapter 边界解密。
4. 真实调用继续使用现有工作区并发、RPM、每日次数、token、OCR、图片和可选成本估算上限。
5. 开源产品不保存余额、不售卖额度、不代收模型费用；API Key 由 Admin 自行提供，账单关系只存在于使用者和模型供应商之间。
6. Demo 只使用 Mock，不能调用使用者 API Key 或写入正式数据。
7. 计划和运行历史进入轻量备份时只保留安全元数据；完整备份按既有授权边界处理正文和对象。
8. 所有自动生成内容继续显示固定风险免责声明，不承诺平台审核通过。

## 16. API 合同建议

第一版建议提供：

- `GET /v1/workspaces/{workspace_id}/agent/briefing`
- `POST /v1/workspaces/{workspace_id}/agent/briefing/refresh`
- `POST /v1/workspaces/{workspace_id}/agent/plans`
- `GET /v1/workspaces/{workspace_id}/agent/plans/{plan_id}`
- `POST /v1/workspaces/{workspace_id}/agent/plans/{plan_id}/approve`
- `POST /v1/workspaces/{workspace_id}/agent/plans/{plan_id}/reject`
- `GET /v1/workspaces/{workspace_id}/agent/runs`
- `GET /v1/workspaces/{workspace_id}/agent/runs/{run_id}`
- `GET /v1/workspaces/{workspace_id}/agent/confirmations`
- `POST /v1/workspaces/{workspace_id}/agent/runs/{run_id}/confirmations`
- `POST /v1/workspaces/{workspace_id}/agent/runs/{run_id}/cancel`
- `POST /v1/workspaces/{workspace_id}/agent/runs/{run_id}/retry`

写接口继续使用会话、CSRF、角色权限和幂等键。读取与写入均重新验证工作区、平台、账号和资源归属。

## 17. 测试与验收

### 17.1 单元与合同测试

- 确定性候选生成和优先级排序。
- 同一输入、算法版本和工具版本得到相同计划。
- 模型不能添加未知工具或越权参数。
- 账号切换、数据版本变化和配置变化使批准失效。
- 角色权限和动作确认矩阵。
- 外部 API 用量、unknown 结果和重试边界。
- 状态机合法与非法转移。
- 日志、备份和 API 响应不泄露敏感正文或密钥。

### 17.2 隔离与故障测试

- 跨工作区统一 404。
- 抖音与小红书候选、事实、风格、指标和风险资料不混用。
- 旧 Worker 无法覆盖新运行状态。
- Provider 成功后落库失败、对象写入失败和补偿失败。
- Redis、数据库、对象存储或 Worker 中断后的安全恢复。
- 重复批准、重复确认、过期确认和幂等冲突。

### 17.3 Web 与 E2E

使用合成双平台数据完成：

1. 工作台生成一项今日建议。
2. 用户查看依据并批准计划。
3. 智能体执行分析、事实与风格检索、草稿生成和风控。
4. 外部 API 步骤在 Mock E2E 中记录模拟用量，不调用外网，也不出现充值或平台付费入口。
5. 页面展示步骤进度、最终草稿、风险结果和人工发布提示。
6. 刷新、重启和重新进入后恢复同一运行。
7. Viewer 只能查看，Editor 和 Admin 权限符合矩阵。
8. 390px 下可以查看、批准普通计划和跟踪进度。

### 17.4 第一版验收标准

在不调用真实平台和不自动发布的前提下，一名运营人员可以独立完成：

> 发现一个账号问题 → 看懂优先原因 → 批准计划 → 等待自动分析和生成 → 查看事实与风险依据 → 保存或导出优化草稿。

验收必须记录首次完成耗时、需要帮助次数、失败步骤、用户是否理解“自备 API Key、供应商可能计费、产品不代收费用”和人工发布边界。独立非开发者测试未完成前，不将智能体标记为正式可用。

## 18. 开发拆分建议

实现计划预计拆成 8 个 Task：

1. 数据模型、权限矩阵、状态机和工具合同。
2. 巡检候选、确定性排序和每日 briefing API。
3. 结构化计划生成、批准失效和工具目录。
4. 异步执行器、步骤审计、幂等、租约和恢复。
5. 现有分析、事实、风格、爆款、生成和风控工具接入。
6. 外部 API 用量治理、正式数据覆盖和回收站确认接入。
7. 今日建议卡、智能体页面、待确认事项、可恢复进度与产物体验。
8. 全链路 E2E、故障注入、视觉回归和非开发者验收材料。

每个 Task 独立提交并通过相关模块回归后暂停，不在同一 Task 内同时扩大工具范围和修改既有业务算法。
